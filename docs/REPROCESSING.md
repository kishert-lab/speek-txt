# Повторное распознавание и ревизии

## Общая схема

Повторное распознавание работает отдельно от опубликованной стенограммы:

1. Пользователь выбирает реплику и режим обработки.
2. Celery создаёт кандидата и распознаёт только выбранный интервал.
3. Пользователь сравнивает опубликованный текст с кандидатом, исправляет текст и говорящего.
4. Кнопка **«Опубликовать ревизию»** явно подтверждает замену.
5. Backend проверяет `base_revision`, захватывает Redis-блокировку задания и атомарно обновляет JSON, TXT и DOCX.

До публикации кандидат не влияет на основную стенограмму и экспортные файлы.

## Статусы

- `queued` — кандидат ожидает Celery worker.
- `started` — выполняется повторное распознавание.
- `candidate` — результат готов к пользовательской проверке.
- `published` — кандидат опубликован.
- `discarded` — кандидат отклонён пользователем.
- `failed` — обработка завершилась ошибкой.
- `superseded` — опубликованная ревизия заменена следующей.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/v1/protocols/{job_id}/reprocess` | Создать кандидата. |
| `GET` | `/api/v1/protocols/{job_id}/reprocess` | Получить кандидатов задания. |
| `GET` | `/api/v1/protocols/{job_id}/reprocess/{task_id}` | Получить состояние и результат кандидата. |
| `POST` | `/api/v1/protocols/{job_id}/reprocess/{task_id}/publish` | Опубликовать проверенный кандидат. |
| `POST` | `/api/v1/protocols/{job_id}/reprocess/{task_id}/discard` | Отклонить кандидат. |
| `GET` | `/api/v1/protocols/{job_id}/revisions` | Получить историю опубликованных ревизий. |
| `GET` | `/api/v1/protocols/{job_id}/revisions/{revision}` | Получить снимок выбранной ревизии. |
| `POST` | `/api/v1/protocols/{job_id}/revisions/{revision}/restore` | Восстановить снимок как новую ревизию. |

Пример создания кандидата:

```json
{
  "start": 125.2,
  "end": 141.8,
  "mode": "asr",
  "context_seconds": 2,
  "base_revision": 3
}
```

Пример публикации после ручной проверки:

```json
{
  "base_revision": 3,
  "segments": [
    {
      "candidate_index": 0,
      "text": "Исправленный текст реплики",
      "speaker_id": "SPEAKER_02"
    }
  ]
}
```

## Конкурентность и восстановление

Публикация выполняется под блокировкой `protocol-revision:{job_id}`. Несовпадение `base_revision` возвращает `409 REVISION_CONFLICT`. Повторная публикация уже опубликованного кандидата возвращает текущий результат и не создаёт новую версию.

Экспорты сначала формируются во временных файлах `*.next`, после чего переключаются через `os.replace`. Маркер `revision-transaction.json` позволяет восстановить согласованные экспорты по текущему `result.json`, если процесс был аварийно остановлен между заменами файлов.

Восстановление старой версии не удаляет историю: создаётся следующая опубликованная ревизия.
