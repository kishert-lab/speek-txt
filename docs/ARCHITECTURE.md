# Полное описание и архитектура

## 1. Назначение

Система предназначена для локального протоколирования русскоязычных заседаний, совещаний, судебных заседаний, конференций и интервью. Исходные записи и результаты остаются внутри инфраструктуры. Внешний доступ требуется только при первоначальном скачивании моделей, если модели ещё не размещены локально.

Функции системы:

- загрузка одного или нескольких аудио/видеофайлов одной встречи;
- сохранение порядка частей и объединение в общую временную шкалу;
- приведение звука к PCM16, mono, 16 kHz;
- отдельная предобработка звука для распознавания и диаризации;
- определение говорящих и перекрывающейся речи средствами PyAnnote;
- распознавание русской речи GigaAM v3;
- словарная коррекция устойчивых ошибок;
- отображение позиции в очереди и прогресса этапов;
- редактирование стенограммы с синхронизацией по таймкоду;
- воспроизведение оригинальной и нормализованной дорожки;
- экспорт JSON, TXT и DOCX;
- сохранение ручных исправлений для пакетной подготовки датасета;
- опциональная запись с микрофона через WebSocket;
- мониторинг очереди, CPU и GPU.

## 2. Контейнерная схема

```text
Browser / API client
        |
        v
      Nginx
       |  \
       |   +--------------------> Frontend (React/Nginx)
       v
   FastAPI API
       |  \
       |   +---- metadata/status/events ----> Redis
       |                                      |  ^
       +---- files ------------------------> /data |
                                              |  |
                           Celery task --------+  |
                                              v  |
                                         Offline worker
                                       PyAnnote + GigaAM

WebSocket client -> API -> Redis Streams -> stream-worker
                                           |
                                           +-> live GigaAM events
                                           +-> WAV -> Celery offline task
```

### API

FastAPI принимает multipart-загрузки по частям по 1 MiB, проверяет суммарный размер, сохраняет файлы в каталог задания и публикует Celery-задачу. API не загружает ML-модели, поэтому остаётся лёгким и продолжает принимать файлы, пока worker занят.

### Offline worker

Celery worker выполняет полную обработку. Настроены позднее подтверждение сообщения (`task_acks_late`), повторная постановка при потере процесса (`task_reject_on_worker_lost`) и prefetch равный единице. Это уменьшает риск потери долгой задачи при аварии контейнера.

### Stream worker

Отдельный процесс читает входные Redis Streams, ведёт bounded queue, сохраняет PCM в WAV, выполняет простой online VAD и предварительную идентификацию говорящих. Доступ к GigaAM внутри одного процесса ограничен семафором GPU. После `stop` создаётся обычная Celery-задача для авторитетной офлайн-диаризации и распознавания.

### Redis

Redis хранит:

- `job:<uuid>`: JSON-метаданные задачи;
- стандартную очередь Celery `celery`;
- `server:worker-metrics`: краткоживущие GPU-метрики;
- `streams:active`: активные потоковые сессии;
- `stream:<uuid>`: состояние сессии;
- `stream-input:<uuid>`: входные команды и аудиофрагменты;
- `stream-events:<uuid>`: события для клиента.

Redis запущен с AOF (`--appendonly yes`). Файлы задания находятся не в Redis, а в Docker volume `protocol_data`.

## 3. Офлайн-конвейер

```text
original / original_0001...
        |
        +-> ffprobe и проверка
        |
        +-> original.wav       оригинальная дорожка для плеера
        +-> diarization.wav    щадящая обработка для speaker embeddings
        +-> normalized.wav     обработка для GigaAM
                                  |
                             PyAnnote diarization
                                  |
                           интервалы говорящих
                                  |
                         разбиение длинных интервалов
                                  |
                          GigaAM transcription
                                  |
                         словарная коррекция
                                  |
                   стенограмма + участники + экспорт
```

Этапы и диапазоны прогресса:

| Этап | Статус | Примерный прогресс |
|---|---|---:|
| Ожидание | `queued` | 0% |
| Проверка | `validating` | 5% |
| Подготовка аудио | `audio_conversion` | 15% |
| Диаризация | `diarization` | 18–48% |
| Распознавание | `transcription` | 50–78% |
| Словари | `correction` | 80–86% |
| Формирование | `protocol_generation` | 88% |
| Экспорт | `export` | 92–97% |
| Завершение | `completed` | 100% |

Процент внутри диаризации и распознавания рассчитывается по числу обработанных элементов. Поэтому длительное нахождение на одном проценте не обязательно означает зависание: отдельный сегмент или batch может обрабатываться долго.

## 4. Аудиоподготовка

Допустимые расширения: WAV, MP3, M4A, AAC, FLAC, OGG, OPUS, WEBM, MP4, MKV и MOV. Расширение проверяется до постановки в очередь, фактическая читаемость проверяется `ffprobe` в worker.

Если передано несколько файлов, они обрабатываются в порядке multipart-полей `files` и затем объединяются. Временные метки результата относятся к общей объединённой дорожке.

Нормализованная дорожка по умолчанию получает:

```text
highpass -> dynaudnorm -> alimiter -> PCM16 mono 16 kHz
```

Для диаризации используется отдельный `DIARIZATION_AUDIO_FILTER`. Сильное шумоподавление и агрессивное усиление могут улучшить слышимость текста, но ухудшить speaker embeddings и объединить разных людей в одного говорящего. Поэтому профили для ASR и PyAnnote разделены.

## 5. Диаризация

PyAnnote загружается из `/models/diarization/config.yaml`, переносится на выбранное устройство и инстанцируется параметрами pipeline. В API можно передать точное число говорящих или диапазон. Если числа не указаны, PyAnnote определяет их автоматически.

Основные факторы качества:

- расстояние до микрофона и отношение сигнал/шум;
- реверберация помещения;
- клиппинг записи;
- перекрывающаяся речь;
- значение clustering threshold;
- слишком агрессивная динамическая нормализация;
- короткие реплики, недостаточные для устойчивого embedding.

Если диаризация недоступна и `ALLOW_SINGLE_SPEAKER_FALLBACK=true`, обработка завершается со стенограммой одного говорящего и предупреждением. Для заседаний с несколькими участниками рекомендуется `false`, чтобы ошибка была видна, а не скрывалась fallback-режимом.

## 6. Распознавание и словари

GigaAM использует локальные checkpoint и tokenizer. Длинные интервалы делятся на фрагменты не длиннее `ASR_MAX_SEGMENT_SECONDS`; к границам добавляется padding. FP16 используется только при CUDA.

Текстовые словари располагаются в `/dictionaries`, на хосте это `./dictionaries`. Формат одной строки:

```text
ошибка>исправление;
вариант 1>вариант 2>правильная фраза;
```

Последний элемент является заменой для всех предыдущих вариантов. Поддерживаются UTF-8 и CP1251. Более длинные совпадения применяются раньше коротких.

## 7. Результаты и редактирование

В каталоге `/data/jobs/<job_id>` создаются:

| Файл | Назначение |
|---|---|
| `metadata.json` | состояние и параметры задания |
| `original.wav` или `original_*` | исходные записи/дорожка для прослушивания |
| `diarization.wav` | вход PyAnnote |
| `normalized.wav` | вход GigaAM и нормализованная дорожка плеера |
| `diarization.json` | интервалы говорящих |
| `transcript.raw.json` | результат распознавания до словарей |
| `transcript.corrected.json` | результат после словарей |
| `result.json` | итоговый API-объект |
| `protocol.txt` | текстовый экспорт |
| `protocol.docx` | документ Word; неназванные `SPEAKER_<номер>` выводятся как `Говорящий <номер + 1>` |
| `training-corrections.json` | ручные изменения сегментов, если они были |

В редакторе пустой текст допустим: таким способом удаляется ложноположительный сегмент. Каждое изменение сохраняет исходный распознанный текст, новый текст, таймкоды и speaker ID.

## 8. Retention и обучение

Раз в сутки worker удаляет задания в статусах `completed`, `failed` и `cancelled`, завершённые более `RESULT_RETENTION_DAYS` дней назад. Задания с файлом `/data/training/corrections/<job_id>.json` не удаляются, чтобы сохранить аудио и разметку до экспорта.

Экспорт обучающих примеров запускается вручную:

```bash
make training-export
```

Команда собирает исправленные сегменты в отдельный датасет. Само обучение модели в сервис не встроено и должно выполняться отдельным контролируемым процессом после проверки качества разметки.

## 9. Масштабирование

CPU-параллелизм библиотек регулируют `OMP_NUM_THREADS`, `MKL_NUM_THREADS` и `OPENBLAS_NUM_THREADS`, но это не увеличивает число одновременно выполняемых Celery-задач.

`--pool=solo` означает один слот задачи в процессе. Для нескольких параллельных файлов необходимо запускать несколько worker-контейнеров/очередей. На GPU с 4 GiB памяти одновременная загрузка нескольких PyAnnote/GigaAM процессов обычно приводит к нехватке VRAM или деградации. Практичная схема:

- один GPU worker для ML-задач;
- отдельные API и stream-worker;
- параллельная загрузка и проверка файлов на API;
- горизонтальное масштабирование ML только при наличии нескольких GPU или достаточной VRAM.

## 10. Безопасность и ограничения

- Имена файлов очищаются, path traversal блокируется.
- Размер проверяется по сумме всех файлов встречи.
- `.env`, модели, записи и словари исключены из Docker build context.
- Модели монтируются как read-only volume и не должны попадать в образ worker.
- HTTPS обязателен для доступа браузера к микрофону, кроме `localhost`.
- WebSocket должен использовать `wss://` на HTTPS-странице, иначе браузер блокирует mixed content.
- Текущие REST-маршруты необходимо защищать внешним доступом до появления полноценной аутентификации.
