# Документация сервиса протоколирования

Сервис преобразует одну или несколько аудиозаписей заседания в стенограмму с таймкодами и разделением по говорящим. Распознавание выполняет GigaAM v3, диаризацию выполняет PyAnnote. Результат доступен через REST API и веб-интерфейс, может быть отредактирован и выгружен в JSON, TXT и DOCX.

## Быстрый запуск

```bash
cp .env.example .env
make models-download
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build
docker compose ps
curl http://localhost/health/ready
```

Веб-интерфейс открывается на `http://<server>:${HTTP_PORT}`. Интерактивная схема FastAPI доступна по `/docs`, если она не закрыта внешним reverse proxy.

## Назначение компонентов

| Компонент | Назначение |
|---|---|
| `nginx` | Единая точка входа, проксирование API, WebSocket и аудиофайлов |
| `frontend` | React-интерфейс загрузки, контроля очереди, редактирования и экспорта |
| `api` | FastAPI: загрузка, статусы, результаты, файлы и метрики |
| `worker` | Celery worker для точной офлайн-обработки |
| `stream-worker` | Долгоживущие потоковые сессии и предварительное распознавание |
| `redis` | Брокер Celery, состояния задач, очередь и Redis Streams |
| `protocol_data` | Аудио, метаданные, результаты и исправления |

## Основной сценарий

1. Клиент загружает файлы в требуемом порядке.
2. API сохраняет их, создаёт метаданные и ставит одну задачу в Celery.
3. Worker проверяет аудио, объединяет части и подготавливает отдельные дорожки для PyAnnote и GigaAM.
4. PyAnnote определяет интервалы и говорящих.
5. GigaAM распознаёт сегменты, затем применяются словари исправлений.
6. Сервис создаёт `result.json`, `protocol.txt` и `protocol.docx`.
7. Пользователь назначает имена, слушает оригинальную или нормализованную запись и исправляет сегменты.
8. Исправления сохраняются отдельно для последующего экспорта обучающего датасета.

## Фактические ограничения текущей версии

- Поддерживается только русский язык (`language=ru`).
- Автоматическое смысловое извлечение решений и поручений пока отсутствует: используется `NullProtocolSummarizer`.
- HTTP-маршруты не выполняют прикладную аутентификацию. Продакшен-доступ необходимо ограничивать внешним proxy/VPN до реализации авторизации.
- Потоковое распознавание предварительное. После остановки запускается точная офлайн-обработка всей записи.
- Один процесс worker с `--pool=solo` одновременно исполняет одну ML-задачу, независимо от значения `--concurrency`.
- Исправленные задания намеренно не удаляются недельной очисткой, пока нужны для подготовки датасета.
